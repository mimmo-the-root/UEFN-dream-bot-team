Learning step (planner-docs step 4b), also forced by hand. Order: CODE (complete sources), then DOCUMENTS compared with the code, then the DEVICES in the level. Never cut the output of a batch with head/cut/tail: every batch ends with a receipt token and `learned`/`docsdone` refuse any other token, so a cut-off read cannot be marked as done.

1. MCP mode, with one call to `mcp__unreal-mcp__call_tool` (the ONLY entry point of the UEFN MCP; `ValkyrieToolset.VerseToolset.ListFiles` is not a separate tool: `toolset_name` = `ValkyrieToolset.VerseToolset`, `tool_name` = `ListFiles`, `arguments` = `{}`; see `~/.claude/skills/mcp-tool-contracts/SKILL.md`). A schema error means the tool exists: read the schema and RETRY until it answers; report the project name it returns. `live` only with that answer; `offline` only if there is no `call_tool` or it fails with a connection error (say which).
2. `Claude/docs/.genre` must name the genre. Empty: work it out yourself from the map (INDEX.md, SPEC/README) and the closest slug of `fortnite-genres-official.json` (always a slug of that list, chosen by the structure of the game with the `hint` of each genre: players, round length, lobby; a new mechanic such as pillars is learned inside its genre; if the owner corrects the genre it is final). Do NOT write `.genre` or create the genre skill yourself: run `python Claude/hooks/skills_lib.py propose-genre <slug> --variant <map-type> --why "<facts that decided it>" --project .` (map type = short free name for this kind of map, e.g. pillars, red-vs-blue; reuse a type already known in that genre when it fits; `python Claude/hooks/skills_lib.py` state is on the console). It is a PROPOSAL: the owner confirms genre and type on the console (Skills page); until then `skills_lib.py` answers GENRE NOT CONFIRMED: lessons are held by the kit and the blueprint stays in `Claude/docs/map/profile.json`; when the owner confirms on the console both are saved by themselves (nothing to retry, never ask in chat, keep reading the project locally). A project that already has a confirmed genre skips this. IP RULE: if the documents (INDEX/SPEC/README/design notes) say the map is a version of the same base game dressed for an IP or franchise, the map TYPE is that IP as a short kebab-case name (the same base game with a different IP = the same genre, a different type); a map with no IP, or the shared base itself, is type `base`. Take it from the documents, never ask the owner in chat; he confirms it on the console. The blueprint of an IP variant records only what DIFFERS from the base (custom devices, rules, numbers) and points to the base blueprint for the rest.
3. Code: (a map with NO Verse files, only devices, skips steps 3-5: go to step 6 and 7) run `verse_map.py learn`. It prints the next batch: for each unread file its brief card and its COMPLETE source. Read it all. Repeat steps 3-5 until it says 0 files to read (the first pass reads every file completely; afterwards only the files that changed).
4. From that batch find reusable, generalized rules (no map names, ids, links): check `skills_lib.py patterns <genre>`, reuse existing wording, queue with `skills_lib.py propose --section <id>` (`<id>` from `~/.claude/skills/genre/<genre>/references/starter-sections.json`: run-loop, architecture, devices, progression, death-strategies, persistence, performance, launch-checklist; `for`, or `against` when the code shows the opposite). No minimum count; the owner approves on the Skills page. Never invent numbers.
5. Assign a section to every pattern whose `section` is null (`skills_lib.py patterns <genre>`, then `skills_lib.py section <genre> <id> <section>`), then run `verse_map.py learned <token>` with the token printed at the END of the batch. Then run `skills_lib.py similar <genre>`: it lists pairs of patterns that say almost the same; report them to the owner (do not merge by yourself) so duplicates can be consolidated. Back to step 3.
6. Documents (after the code): `verse_map.py docs` prints the next batch of documents complete, each followed by "possible drift vs code map". Read every document fully. (a) Learn the owner's DESIGN decisions as patterns, with `--section`. The documents are the main source for sections progression, death-strategies and launch-checklist (the code only shows bug fixes): extract what the owner decided about how progression works (what persists, what resets, unlocks, currencies, difficulty), what happens on death and retry, rewards, retention, and every test/launch checklist item, written as general rules (condition -> action), not as this map's names. For each of those three sections report which document supports it or say plainly "no generalizable rule found in <documents>". (b) COMPARE with the code you just read: confirm each drift item with `verse_map.py symbol NAME` or Grep; list the real discrepancies (document says X, code shows Y, in which file). (c) REVERSE-ENGINEER the documents from the code and the level: for every discrepancy (stale numbers, files/classes that moved or do not exist, a design marked as draft that is implemented, missing systems) write a patch into `Claude/docs/map/doc-patches.json` as `{"patches":[{"id":"d1","file":"Claude/docs/X.md","find":"<exact text, unique in the file>","replace":"<corrected text>","reason":"...","source":"<code file:line or MCP read>"}]}`, using only facts you verified in the code or the level (mark anything inferred as [I]). A system with no document gets a new `Claude/docs/DESIGN-<system>.md` from `docs-template` (facts from code, intent unknown stays "unknown"). Then run `verse_map.py docpatch list`: it checks that every `find` exists exactly once. Then APPLY the valid ones yourself with `verse_map.py docpatch apply --all` (the script matches the exact text and keeps a backup in `Claude/logs/doc-backup/`; the owner can undo with `docpatch revert <stamp>`). Do not ask first: the documents are derived from the code and must not stay stale. Fix or drop invalid patches. Never touch the code. Never interview the owner: what the code, the documents and the level do not show is reported as "unknown", not asked. EVERY document of the batch needs a recorded decision, or `docsdone` refuses: corrections applied, or `{"reviewed":[{"file":"Claude/docs/X.md","note":"what you verified in the code"}]}` in `doc-patches.json` when it is accurate. Pay special attention to the `[status words to verify against the code]` line: a document that says draft/planned/no code/to do for something the code already implements is stale and MUST get a patch (also update its status line/date). Then `verse_map.py docsdone <token>`; repeat until 0 documents.
7. Devices (automatic, not optional when `live`): READ the level through `call_tool` (read-only; contract "reading the devices placed in the level"): `find_actors` for the device classes the code references (counts), then ALWAYS the wiring and settings: `ListEventBindings` for every placed Verse device (the `VerseDevice_C` instances and the devices the code binds with `@editable`) and `GetDeviceProperties` for the devices that carry gameplay settings (spawners, trackers, barriers, item granters, timers). Do NOT ask the owner whether to read them. Cap: at most 40 devices per pass, most-referenced first; say exactly which were left out and read them in the next pass. An existing device map (`Claude/docs/DEPENDENCY-MAP*.md`, `Claude/docs/map/DEVICES.md`) is the BASELINE to compare with, never a substitute for reading. ALSO read the ISLAND CONFIGURATION (contract "reading the island configuration" in `mcp-tool-contracts`: Island/Experience Settings, team settings, Player Spawner groups) and write a short `## Island configuration` block in DEVICES.md with what you DEDUCE (max players, teams, rounds, time limit, spawn pads and which are a pre-lobby, vehicles per player), each with its evidence; never ask the owner for these. Add the third line `ISLAND-CONFIG-READ: yes|no` at its top. Every deduction rule that worked (for example "a cluster of spawners flagged island-start, hidden and unwired = pre-lobby") is queued as a pattern with `--section run-loop` or `devices` so the next map starts from it. Do this when `Claude/docs/map/DEVICES.md` is missing, `ISLAND-CONFIG-READ` is not yes, or when step 3 read any file (the code changed), or when the owner typed `/learn-map devices` ($ARGUMENTS). Write/update `Claude/docs/map/DEVICES.md` (class, count, wiring: who triggers whom, key settings, what was left out, date) and put these lines at its top, `WIRING-READ: yes|no`, `SETTINGS-READ: yes|no` and `ISLAND-CONFIG-READ: yes|no`, so the next session knows what is missing. Counts alone are not enough, report differences from the baseline, queue device patterns with `--section devices`. If `offline`, list which devices were not inspected. Also write one line `ISLAND-CONFIG-SUMMARY: <players, teams, rounds, time limit>` in DEVICES.md (the console shows it). The console log for devices and island configuration is written by itself from these flags: do not log it by hand.
If the session stops early (out of tokens), nothing else is needed: a batch is marked only by `learned`/`docsdone`, so unmarked work is read again at the next session start. `verse_map.py status` and `Claude/docs/map/PROGRESS.md` list what is missing. Never ask the owner to continue.
8. Map blueprint (the most important result; do it every time the code, the documents or the devices changed, and whenever `PROGRESS.md` says it is NOT written): the genre skill must know HOW A MAP OF THIS KIND IS MADE, not only technical lessons. Write `Claude/docs/map/profile.json` and save it with `python Claude/hooks/skills_lib.py profile <genre> --map "<map name>" --file Claude/docs/map/profile.json --project .` (the map name stays private). Facts only, from the code, the documents, the devices and the island configuration, with the numbers you observed (counts, radii, timers, thresholds); put what you did not read in `unknown`. Shape: `{"variant": "the map type, same name as confirmed on the console", "concept": "one or two sentences: what the game is, how it is won", "layout": [{"element": "Pillars around the centre", "count": "12 + 1 central", "note": "ring, what each one is for"}], "loop": ["ordered phases of one match, with timings"], "devices": [{"class": "Item Granter", "count": 6, "role": "what it gives and when", "settings": "key settings", "wiring": "who triggers it"}], "rules": [{"when": "every N damage dealt", "then": "the granter gives a weapon", "numbers": "N = ..."}], "verse": [{"component": "game manager", "role": "state machine Waiting/InProgress/EndGame", "api": "@editable references, events subscribed, public methods"}], "scoring": ["what gives points or XP, how much"], "build_order": ["1. place ..., 2. ..., in the order someone building this map from zero should follow"], "unknown": ["..."]}`. To let the map be REBUILT from an empty level: positions as formulas (count, radius, angle step, height, size), for every device the settings that differ from the default WITH their values (read them with `GetDeviceProperties`; a setting you did not read goes to `unknown`, and the next pass reads it), and for Verse the components, their states, events and `@editable` references. Write it so that someone who knows nothing about the genre could build a new map of it from `references/starter.md` (Map anatomy). Never ask the owner for these details; infer them. After saving it, in the same pass queue 3 to 5 GENERAL lessons the blueprint teaches (how this kind of map is built: devices that drive the loop, their wiring, numbers that worked; no names, one pattern each; `skills_lib.py patterns <genre>` first, reuse wording) with `skills_lib.py propose <genre> --variant <map type> ...`; the owner approves them on the console. Items left in `unknown` are read by the next session starts (at most two tries each, through the MCP, never invented): the kit tells you when.
9. Report in seven lines (the first six as before; the seventh: the map blueprint saved, with its layout/devices/rules counts): files read (complete) and proposals queued; patterns assigned to a section; documents read and patterns from them; document-vs-code discrepancies with the proposed fix (or "none"); MCP mode with the project name returned; devices read from the level (count per class) and differences from the baseline, or not inspected.
