The demo does the COMPLETE round of the kit on the pilot game Chicken Roundup (the Epic farm example): idea, spec, plan, tasks, the map built in UEFN, audit, delivery list, playtest. `/demo` and `/demo --auto` do exactly the same work; the ONLY difference is that `--auto` never stops to ask. Run it in a NEW empty test project, never in a real map (if there is already the owner's own spec, plan or tasks, stop and say so). Run scripts from `Claude/hooks` (`py -3` on Windows). Input: `$ARGUMENTS`.

- **`/demo` (interactive):** at every approval point ask the owner with AskUserQuestion; the answers are theirs.
- **`/demo --auto`:** no questions. The AI approves every point of the flow on the owner's behalf and writes "approved by the AI (--auto demo)" next to it. It starts, works and finishes by itself.

**First action, always:** `python demo_timer.py start --mode interactive` (or `--mode auto`). If a clock is already running: interactive asks whether to stop it, `--auto` stops it and starts again. If a previous demo is in the docs, `python demo_pilot.py load` moves its files to `_to_delete` (never deletes) and you start from an empty project.

**Inputs of the pilot** (the answers `--auto` uses; interactive proposes them): idea = the farm game Chicken Roundup, collect the escaped chickens and bring them to the pen before the round ends; 4 players, co-op (ask the players first, multiplayer must be guaranteed); forbidden: leaderboard, pvp. The files in `Claude/reference/demo-chicken-roundup/` are the expected result: compare at the end, never copy them.

**The round, each phase timed** with `python demo_timer.py phase "<key>"`: use EXACTLY these keys as the label (a short note may follow after a colon, e.g. `build: T-002`), because the Docs page turns each one into a lit arrow and opens its page by itself. The page shows the total big and the running phase small, so keep the phases in this order and never skip one:
1. `idea`: `/spec` first half: study of the kit's knowledge, three scored variants, the idea chosen.
2. `spec`: `/spec` second half: players asked first (multiplayer guaranteed), loop, stories, risks, Island settings needs, review, approval.
3. `plan`: the constitution and `/game-plan` (Island settings table, the `## Environment` table of the scenery, where each device goes: a DemoDisplay outside the play area, gameplay-position devices in place), review, approval.
4. `tasks`: `/task-list`, then `/consistency`.
5. `environment`: `/environment` (what the owner must have: Beta Access, Python scripting, MCP) AND the scenery BUILT in the map: every row of the `## Environment` table of the plan (ground, sky and light, props, sound, boundary) placed in UEFN and read back, row by row `planned` -> `built`. The demo is not complete with an empty or unfinished environment.
6. `build`: for EACH task, in this order: set its ROADMAP row to `In progress` and run `python demo_timer.py phase "build: T-00N"` BEFORE touching UEFN; build it; when its check passes set the row to `Done` and only then start the next. Never leave a row at `To do` while you work on it: the Docs page and the owner follow the file. The gameplay in UEFN task by task with the `coder` agent (plan first, approval before each change, Verse with editable parameters instead of references the MCP cannot assign, Island settings set and read back, build clean), validation and review after each step. Check the Verse digest for what the game needs before choosing the mechanic; if a command does not exist, say it in the plan and use the nearest one.
7. `audit`: `/audit` (fix minor findings alone, record serious ones with the recommendation), including the Fab and island compliance scan and the placement check.
8. `delivery`: `/delivery` (what only the owner can do, private release, Publishing Validation and memory flags to confirm) and `/environment --playtest` with the real number of players. Stop here: the private release and the publish are the owner's.

Update the roadmap task statuses (To do, In progress, Done) the moment they change, edit the file right away and not at the end: the Docs page follows them live and a row that stays `To do` while you work looks like a stuck demo.

**Scenery and devices.** The scenery, the devices and the Verse are built by the `coder` (or the main session) with direct MCP calls, read back and kept; the agents `mcp-level`, `mcp-build` and `mcp-material-vfx` are the guarded exploration lab and are never used for the pilot (they refuse game writes by design). Before the plan and before placing anything, read `Claude/docs/demo-chicken-roundup/SCENERY.md` (proven asset names, sizes, devices and traps of the farm). The chickens are `Device_WildlifeSpawner_V2` with the animal read and set, not Item Spawners or triggers. The environment rows are `built` only with real assets read back; cubes are `placeholder` and the demo reports them as missing.

**Stop on red (your turn).** When a task cannot go on without something only the owner can do (device references the MCP cannot assign, a setting only the owner can change), write each action as a line of the checklist, one command per action: `python Claude/hooks/owner_steps.py add setup "<exactly what to do>" "<which device, which field, where>"`. Set the task row to `Blocked: <the same words>` and run `python demo_timer.py phase "your turn: owner steps"`. The console shows them as step 8 "Your turn" with a Done button each. Then WAIT without asking the owner to write to you: run `python Claude/hooks/owner_steps.py wait setup` (it returns when every item is ticked; if it says "still waiting", run it again). You never tick a box. When it returns: read the references back (`GetDeviceProperties`), `BuildAll` clean, set the row `Done`, go on by yourself. Works also with `--auto` (an owner-only step cannot be automated). No `/audit`, no `StartSession` or `StartGame`, no "the mechanic works" while an item is open.

**First step of the build, before anything is placed.** List the actors and folders of the map. (1) Delete what the new map brings and the plan replaces (the default player pads: `find_actors` name `Spawn Pad`, `remove_from_scene`), then place the new ones and read back that only they remain. (2) Whatever the owner placed or configured by hand (assets, the egg, the damage volume and its settings) is kept untouched: read its transform and settings and write them in `map/DEVICES.md` under "Placed by the owner", and reuse them. (3) If the owner changed the mechanic, update `GAME-SPEC.md`, the plan, the roadmap, the Verse and the playtest in the same pass and remove the old device from the map. The recipe is `SCENERY.md`: the pen scores with the egg and its damage volume, never with a capture area.

**Placement check.** After every device or prop read its location against the zones (egg and damage volume, spawn area, boundary). A device that is wrongly placed is MOVED and read back, never only reported.

**Final confirmation (last step).** At `delivery`, after `/audit`, write the gameplay checks for the owner: `python Claude/hooks/owner_steps.py from-spec` (one box for each player action of the GAME-SPEC loop: action, rule, reward, end, replay; the main things the player does, not every task; add more with `add gameplay` only for something the loop does not cover), run `python Claude/hooks/owner_steps.py wait gameplay`, and only a ticked box means the game was played and works. Anything the owner reports after playing becomes a task, then the owner plays again.

**A playtest needs a player.** `StartSession` / `StartGame` / `StopGame` through the MCP start a match with nobody in it: the editor stays in editing mode, nothing of the gameplay runs for a person and no game log proves the loop. Never report that as a playtest or as a task being verified; verify a task with a clean `BuildAll`, the read-back of the device properties and, if the Verse has `[SIGNAL]` log lines, the lines in the editor log. The real playtest is the owner's, in the Fortnite client, with the checklist of `PLAYTEST.md` (phase `delivery`). Each `StopGame` also wakes the automatic post-playtest checks, which waste a run on an empty match.

Never launch or relaunch UEFN; if it or the MCP is not reachable, stop the clock and say why. Never delete: park in `_to_delete`. When the last file exists run `python demo_timer.py stop`, then `python demo_timer.py report`.

At the end say in a few lines what was made, the total time, the slowest phase, what the audit found and what is left for the owner. Do not edit the demo reference files.
